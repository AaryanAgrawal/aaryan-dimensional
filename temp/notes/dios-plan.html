Full plan · 2026-08-10

dios

One repo, one binary. The package manager and the robot provisioner stop being two products. Plus the thing that actually decides the architecture: shipping to China, where the URLs everything depends on do not resolve.

One binary

The command becomes dios, and infect folds into the same repo as a subcommand tree rather than a second product.

dios setup                  install dimos on THIS machine        the package manager
dios install <pkg>          add a package
dios doctor [--json]        what is this machine, what is wrong
dios config · log · self    settings, history, self-update

dios infect                 set up a ROBOT                        the provisioner
dios infect scan            find robots on usb/bt/wifi/ethernet
dios recipe {new,list,show,test,add,remove}

The boundary that took a day to draw does not change — it stops being a repo boundary and becomes a module boundary. src/pkg/ knows platforms and may never mention a robot; src/infect/ knows robots and calls into pkg the way it used to shell out to a second binary.

What we lose, honestly. Two repos enforced the boundary — infect could only reach helm through a CLI contract, so a leak was a compile error. In one repo, nothing stops pkg importing something from infect except discipline. Replace the enforcement with a test: assert that no module under src/pkg/ references infect, and fail the build if it does. Cheap, and it keeps the property that mattered.

Against that, the merge buys real things: one install, one version, one release, no cross-repo contract drift — which the review named as the top long-term risk — and no way for the two halves to disagree about JSON they both know at compile time.

The G1, reliably

The target: a fresh G1 out of the box to dimos run unitree-g1, with one command and two prompts. Every step below is a line from Krishna's guide with a machine-checkable proof attached.

  4 jetson-perf    nvpmodel -m 0 + jetson_clocks          nvpmodel -q says MAXN
  5 git transport  https instead of ssh for github        git config --get returns it
  6 cyclonedds     build 0.10.x from source (~15 min)     ~/cyclonedds/install exists

  9 config         blueprint + transport written          dimos run works with no arguments

  Done. Controller in hand and a gantry before first stand.

Three details in there are the difference between working and not, and all three come from the guide rather than from theory. The wifi step must write an explicit wpa-psk profile, because nmcli device wifi connect fails on 20.04 with Secrets were required (7) — the WPA3 handshake breaks against that wpa_supplicant. Step 3 proves untethered ssh before you unplug, so a failure cannot strand you. And step 8 must run after step 7 and verify in a fresh shell, because the Python bindings need the venv dios setup creates, and CYCLONEDDS_HOME is exported after the installer's own check.

The cheap question that invalidates everything, and is still unanswered. The G1 prints a ros:foxy(1) noetic(2) selector on login. If that is not guarded on interactivity, every non-interactive ssh step hangs and the whole verb layer is wrong. One ssh unitree@10.0.0.190 'echo hi' settles it. Do this before writing another line of the G1 path.

Orin and Nano

These are boards, not robots, so they are a dios setup problem rather than an infect problem — nothing needs identifying or reaching. What varies is entirely platform, which is exactly what the package manager is for.

BoardJetPackUbuntu · glibcWhat breaks
Jetson Nano4.x18.04 · 2.27below almost every manylinux floor; dropped by JetPack 5+. Must degrade with a clear message, not crash or half-install
Orin Nano622.04 · 2.35clears the wheel floors. CUDA 12 from JetPack, not from a wheel
AGX Orin622.04 · 2.35same as Orin Nano, more RAM
Orin NX (the G1)5.1.120.04 · 2.31the measured reference. Below the 2.34 floor, so unitree and base get excluded and a substitution carries the driver

The work is not per-board code. It is making doctor honest on each — that a Nano is told plainly it is too old rather than being handed an install that fails at import, and that CUDA is reported from /etc/nv_tegra_release plus nvcc when nvidia-smi does not exist. Both already landed. What is missing is a fixture per board asserting the decision, which the test matrix has written.

China — the problem that decides the architecture

A fresh install reaches out to six places, and in China roughly all of them are slow, throttled, or gone.

archive.ubuntu.com      apt: portaudio, git-lfs, libturbojpeg, build tools
pypi.org                every Python wheel — gigabytes, and the long pole
github.com              dimos itself, CycloneDDS source, the Unitree SDK
nixos.org               the Nix installer
cache.nixos.org         every prebuilt Nix path
R2 / ghcr.io            the dios binary, container images

Two answers, and you want both

Mirrors handle the ordinary case. This is what every engineer in China already does, and it is a configuration change rather than an architecture:

apt    mirrors.tuna.tsinghua.edu.cn/ubuntu          or aliyun, ustc
pip    pypi.tuna.tsinghua.edu.cn/simple
nix    mirrors.tuna.tsinghua.edu.cn/nix-channels/store  as a substituter

So dios setup --region cn rewrites sources before the first fetch. Cheap, boring, and it turns a two-hour install into a normal one. Do this first.

An offline bundle handles the real case — the customer site with no useful internet, the demo, the shipment. And the mechanism already exists in the codebase, built for a different reason.

# helm already does this — docker.rs, the DIMOSPAK payload
[ELF binary][zstd-compressed tar][u64 size LE][DIMOSPAK]
      ↑                ↑
   the dios CLI    a complete DimOS image

run/pack_docker <dios-binary> <image>  →  one file, no registry, no network

A binary with an image glued to its tail. It reads its own file at startup, finds the marker, and installs from the payload. I described this earlier as being for air-gapped robots — China is that same case, and this is already written and shipping. What it needs is to become a supported release artifact rather than a manual script nobody runs.

Is Nix the answer? Partly, and the honest part matters

Nix's model is precisely "fully compiled binaries, addressed by hash". A binary cache serves prebuilt store paths, and nix copy exports a complete closure to a file you can carry onto a plane. For everything native, that is exactly the thing you asked for.

# on a machine with internet
nix copy --to file:///media/usb/store .#dimos-native-closure

# on the robot, offline
nix copy --from file:///media/usb/store --all

But it does not cover the part that is actually gigabytes.

Where Nix stops

  • The Python ML stack is not in Nix, and putting it there is a project. torch, ultralytics, transformers on aarch64 with CUDA — nixpkgs' story here is weak, and dimos gets them from PyPI through uv. This is the reason "go fully Nix-heavy" does not close, and it is not a small gap: it is most of the install by volume.
  • Disk. Measured: 1.1 GB on the robot after one install, 59 GB on this laptop after months. The store never collects garbage by itself, so a long-lived robot grows until it stops. A GC job is not optional.
  • Root to bootstrap. Creating /nix needs it. Nix concentrates the sudo requirement into one early step rather than removing it.
  • A cold build on a Jetson is brutal. If the cache lacks your derivation you compile from source, and that is where g++: fatal error: Killed signal terminated program cc1plus comes from.
  • It does not manage system state. No systemd units, no /etc, no env vars — on Ubuntu it builds into a store and stops. CYCLONEDDS_HOME stays the installer's job forever.

On hot-loading, since you asked

Nix is better than apt at the thing people usually mean and worse at the thing you probably mean.

Switching profiles is atomic: a new generation is built, then one symlink flips. There is no window where half the packages are upgraded, and rollback is flipping it back. That is strictly better than dpkg unpacking files over a running system.

What is genuinely hard is partial and incremental change. You get whole closures, not one swapped library. A running process holds its old store paths open — which is a feature, since nothing breaks mid-run — but it means picking up a change requires a restart. And you cannot add a dependency into a live environment the way uv pip install can.

The tension worth naming before committing. We designed dependencies install on run — a blueprint hits ModuleNotFoundError, fetches the extra it needs, retries. That is a dynamic, incremental model. Nix is a static, whole-closure model. They pull in opposite directions, and "very Nix heavy" quietly means giving up on-run installation for anything Nix owns.

The resolution is the split that already exists in dimos, and it is the right one: Nix owns native modules, where closures are small, builds are expensive and reproducibility is worth everything — fourteen modules already declare a Nix build. uv owns Python, where the graph is huge, changes are frequent, and on-run installation is the feature. China does not change that boundary; it changes how each side is delivered — a mirror or a closure for Nix, a mirror or a wheelhouse for Python.

PYTHON, offline:   pip download -d wheelhouse/ 'dimos[unitree]'
                   pip install --no-index --find-links wheelhouse/ 'dimos[unitree]'
                   a directory of wheels, carried like a Nix closure

The scanner

Going into todos rather than the build, because it is the natural front door and it wants the transport work underneath it first.

$ dios infect scan
  usb        Jetson at 192.168.55.1                  l4t device mode
  ethernet   carrier on enp0s31f6, 192.168.123.164   two jacks, this is the live one
  wifi       unitree-go2 · port 9991 open · 10.0.0.213
  bluetooth  GO2_1581 advertising                     Go2 pairs over BLE first

  2 candidates. [1] unitree-g1 (wired)  [2] unitree-go2 (wifi)

Each transport is a read-only probe over an existing surface: link carrier plus a subnet sweep for ethernet, usb0/l4tbr0 and 192.168.55.1 for USB, mDNS and a port sweep for wifi, and a BLE advertisement scan for Bluetooth — which matters because a fresh Go2 announces itself over BLE before it is on any network at all. The recipes already declare what to look for; scan is that vocabulary run without a target in mind.

Order

  1. Settle the G1 login shell. One ssh command. It invalidates the verb layer if it goes the wrong way, and everything else assumes it.
  2. Rename to dios and merge the repos. Do it before more code accretes, and add the test that forbids pkg from referencing infect.
  3. --region cn. Mirror rewriting for apt, pip and Nix. Small, and it is the difference between usable and not for a whole office.
  4. The G1 end to end, against the fake-Jetson container first, then the real robot. This is the reliability goal.
  5. Record real facts. dios infect probe --record on the G1 — read-only, and it converts every fixture from an assertion about a document into one about a robot.
  6. The offline bundle as a real release artifact: the DIMOSPAK payload plus a Python wheelhouse plus a Nix closure, produced by CI rather than by a script someone remembers.
  7. Orin and Nano fixtures, then a real board when one is free.
  8. The scanner, once transports exist.

Open

  • Does the G1 login selector hang a non-interactive ssh? Unanswered, cheap, and load-bearing.
  • Whose tailnet. Still unresolved, so Tailscale stays opt-in.
  • go2web's build and fetch story. dimensionalOS/go2web is private and unread from here; payload.deliver needs it.
  • Which mirror. Tsinghua, Aliyun and USTC all work; the Shenzhen office may already have a preference, and matching it beats picking one.
  • Is there an internal binary cache? If Dimensional runs one, --region cn becomes pointing at it rather than at a public mirror, and that is strictly better.
