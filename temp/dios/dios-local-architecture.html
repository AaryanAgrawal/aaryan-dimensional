Dimensional · Proposed architecture

How dios works

Keep the existing DimOS Helm experience in dios core. Put every manufacturer's robot knowledge and wizard in that manufacturer's own repository.

The central rule: dios setup installs DimOS on the machine where it runs. It works the same way on a developer workstation and on a robot target. A manufacturer wizard gets the target ready, invokes that standard setup, then performs manufacturer-specific finishing and verification.

1. Three repository types

dios core

  • Existing Helm commands
  • dios setup
  • doctor, update, service, logs
  • DimOS installation UX
  • Local target/version history
  • Manufacturer wizard launcher

Manufacturer repo

  • Its setup wizard
  • Robot models
  • Discovery and identification
  • Network bring-up
  • Firmware checks
  • Manufacturer-specific setup

DimOS repo

  • DimOS package
  • Modules and extras
  • Runtime requirements
  • Blueprints
  • Release versions

Examples of manufacturer repositories:

dios                         generic core
dios-unitree                 Unitree wizard, G1, Go2, B2, ...
dios-agilex                  AgileX wizard and models
dios-universal-robots        UR wizard and models

2. User-facing commands

CommandWhat happensOwner
dios setupInstall DimOS on this machine using the familiar Helm flow.dios core
dios doctorCheck whether this machine is ready for DimOS.dios core
dios updateUpdate dios safely.dios core
dios seed unitreeDownload or load the Unitree integration and open its wizard.dios launches; Unitree owns experience
dios target listShow targets previously seeded from this workstation.dios core

3. Installing DimOS on a workstation

This remains close to Helm today:

# Install dios itself
bash <(curl -fsSL https://dim.bot/install.sh)

# Install DimOS on this workstation
dios setup

# Existing choices remain available
dios setup --mode library
dios setup --mode dev

No manufacturer integration is involved. dios detects the workstation, presents the existing setup choices, installs DimOS, configures it, and verifies the local installation.

4. Seeding a robot

dios core
The operator runs dios seed unitree. dios resolves a pinned, verified Unitree integration.
Unitree repository
The Unitree wizard opens. It discovers Unitree targets, identifies the model, and lets the operator choose the robot.
Unitree repository
The wizard establishes access, handles Unitree networking, checks firmware, and prepares the target for a generic DimOS installation.
dios core on the target
The wizard transfers or installs dios on the target and runs the standard dios setup flow there. This is the same setup engine used on a workstation.
Unitree repository
The wizard performs any Unitree-only post-setup configuration and selects the correct Unitree blueprint.
dios + Unitree wizard
The target runs a bounded headless blueprint test. The wizard reports success only if the robot-specific outcome is proven.
dios core
The workstation records the target name, identity, last address, manufacturer integration version, and installed versions locally.

6. What stays from Helm

  • The setup command and its main user journey.
  • Platform detection and compatibility checks.
  • Library versus development installation.
  • Dependency and extras selection.
  • DimOS installation, doctor, service, update, logs, and uninstall.
  • Interactive, unattended, and agent-driven modes.
  • Step-level failure handling and clear recovery instructions.

The work is a refactor and cleanup of this experience—not a replacement.

7. What leaves dios core

  • Unitree, Go2, G1, and other manufacturer names.
  • Manufacturer discovery probes and network assumptions.
  • Manufacturer passwords, firmware rules, and setup guides.
  • Robot-model-specific dependency steps.
  • Manufacturer-specific wizard screens and questions.
  • Manufacturer-specific blueprint selection and final checks.

8. Integration contract

dios only needs a small contract with a manufacturer repository:

Manufacturer providesdios provides
Name, version, supported models, and verified sourceInstallation and update of the integration
Wizard entry pointConsistent launch and mode handling
Discovery and target-selection experienceLocal target records
Pre-setup and post-setup workThe standard dios setup engine
Target-specific final proofCommon result and action logging

9. Local state

For now, dios stores only local JSON configuration and history on the workstation:

  • known target name and stable identity;
  • last-known addresses;
  • manufacturer integration and version;
  • dios and DimOS versions installed;
  • last seed result and timestamp.

No cloud database, account, licensing, or fleet backend is part of this architecture.

10. Decisions still needed

  • Final command form: dios seed unitree versus dios unitree seed.
  • How manufacturer repositories are named and indexed.
  • Whether integrations run as downloaded executables or a defined dios plugin format.
  • How much generic SSH and file-transfer behavior remains in dios versus a shared integration SDK.
  • How the existing dios infect implementation migrates without breaking current work.
