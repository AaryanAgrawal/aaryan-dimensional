End-state architecture · 2026-08-08

dimos-infect

Helm gutted down to platforms and nothing else. Infect owns every robot, with an app per robot and a framework for adding more. Two robots at launch: G1 and Go2. Designed as the destination rather than as a migration, since we build it next.

The rule

Helm knows platforms. Infect knows robots. Nothing else is negotiable, and every ambiguous call resolves with one test: does the compat engine need this fact to pick a wheel? Yes means helm, no means infect.

That test does real work. CUDA passes it — you cannot choose between a CUDA and a CPU torch wheel without knowing. The Jetson's L4T version fails it, even though the two are found in the same place, because nothing about wheel resolution depends on whether this is L4T 35.3 or 36.2. Same directory, opposite sides of the line.

Two identities

The split reads better once each side has a name for what it grows into.

dimos-helm     THE PACKAGE MANAGER FOR DIMOS
                 apt for robots. Resolves and installs packages against a platform.
                 Grows toward: versions, dependency resolution, an index, updates.
                 Stays small, stays universal, never fails.

dimos-infect   THE WAY YOU SET UP A ROBOT
                 One app per robot. Identifies the machine, does the networking,
                 installs payloads, calls helm for packages, and writes the dimos
                 config that makes the robot actually run.
                 Grows outward: more robots, third-party apps.

Helm growing small and infect growing wide is the point. Every new robot is an app, and adds nothing to helm. Every new platform is a helm change, and adds nothing to any app.

The package manager is already half-built. dim install <git-url-or-path> exists today. It records the source under pkgs.installed.<name>, places it in pkgs.dir — cloning a git URL, symlinking a local path so edits show live — and the desktop scans that directory to surface each package's apps. There are twelve references to that vocabulary in the source. install, update and uninstall are all already commands. Calling helm the dimos package manager is finishing what is there, not a new direction.

Three shapes, not two

go2web changes the design. It is a Rust binary that runs on the Go2 and publishes odometry, point clouds and H.264 over Zenoh — so the robot does its own perception while dimos still runs on your laptop. That is a third deployment shape, and the framework has to express it as a first-class thing rather than a special case.

1  HELM ON THE ROBOT                       G1
   ┌──────────┐              ┌────────────────────────┐
   │ infect   │──ssh────────▶│ helm → full dimos      │
   │ (laptop) │              │ blueprint runs here    │
   └──────────┘              └────────────────────────┘

2  HELM ON THE LAPTOP                      Go2, WebRTC lane
   ┌────────────────────────┐         ┌──────────┐
   │ helm → full dimos      │◀──WebRTC─│ robot    │   robot untouched,
   │ incl. PointLio odom    │  :9991  │ (stock)  │   never receives code
   └────────────────────────┘         └──────────┘

3  BRIDGE ON ROBOT + HELM ON LAPTOP        Go2, Zenoh lane  ← go2web
   ┌────────────────────────┐         ┌────────────────────┐
   │ helm → dimos:          │◀──Zenoh──│ go2web bridge      │
   │ mapping, planning,     │         │ PointLio + H.264   │
   │ path following         │──cmd───▶│ onboard            │
   └────────────────────────┘         └────────────────────┘

Shape 3 is the one worth designing for deliberately. It means an app can install a robot-resident payload that is neither dimos nor helm — a small native binary that does the latency-sensitive work onboard and speaks a wire protocol back. That is exactly how you support a robot too weak to run the full stack, and how you'd support a robot whose vendor OS you would rather not touch.

Helm, after the deletion

Everything robot-shaped leaves. What remains is a tool that takes an operating system and gives you a working DimOS on it, and knows nothing else about the world.

What stays, and gets stronger: OS detection, wheel compatibility, uv and venv mechanics, system dependencies, sysctl tuning, the desktop, self-install, update. Plus the CUDA probe, because a developer with an NVIDIA workstation must get a CUDA install by running dim setup and nothing else.

The invariant that decides every hard case. Infect is never a prerequisite for helm. Helm always works alone, on any machine, with no orchestrator. Infect may override a platform fact — and on a Tegra, where the generic probe is unreliable, it should. But override is not supply, and helm cannot depend on being supplied.

Universality work, which is the point of gutting it

  • Parse /etc/os-release properly. Today anything Linux that is not recognised falls through to Ubuntu. Add Debian, Fedora, Arch and a generic Linux, keyed on ID and ID_LIKE.
  • Detect musl and skip the glibc wheel gates rather than computing nonsense.
  • A package-manager layer over apt, dnf, pacman, apk and brew — and for anything unknown, print the commands a human would run and carry on. Degrade, never fail.
  • Wire up the preflight. plan.rs's diagnose and blockers are written, tested and currently dead code. They become the real gate.

The blocker that must land first

Helm's exit code is meaningless today. handle_stage auto-continues every non-critical failure when non-interactive, and all thirteen stages pass critical=false — including "install DimOS" and "verify install". A completely failed install exits 0.

Infect reads that exit code to decide whether to run its post-helm steps. Until it means something, a helm failure surfaces as the wrong error: infect blames its own step for a venv that helm silently failed to create. One accumulator in run_setup fixes it, and nothing else should be built first.

The contract

dim doctor --json
  → {"os":"ubuntu","os_version":"20.04","arch":"aarch64","glibc":"2.31",
     "gpu":"tegra","cuda":"11.4","python":"3.10.12","ram_gb":15,"disk_gb":98,
     "findings":[{"check":"disk","severity":"info|warn|block","detail":"…","fix":"…"}]}

dim plan --json --extras <csv> --mode <library|dev>
  → {"resolved":["base","unitree"],"excluded":[{"extra":"cuda","reason":"no NVIDIA gpu"}]}

dim setup --non-interactive --mode dev --extras unitree --smoke-blueprint unitree-g1
  → exit 0   install verified
    exit 1   {"failed_stages":["install DimOS"]}

Infect never parses helm's human output — only JSON and exit codes. That is what lets helm change its prompts, spinners and stage names freely without breaking every app in the field.

The app model

An app is a directory: a manifest, optional scripts, assets. Three layers.

1  MANIFEST   app.toml — probes, params, lanes, steps, payloads, helm call, notes
              core reads it without executing anything

2  VERBS      core-implemented, idempotent, check/apply/verify
              net.wired-profile · wifi.join · ssh.install-key · jetson.max-perf
              payload.deliver · helm.deliver · sysctl.apply · port.sweep
              the dangerous operations written ONCE — a manifest line inherits the
              WPA2 fix, dry-run and the failure menu for free

3  SCRIPTS    escape hatch for the long tail (the CycloneDDS build)
              timeout-bounded, declared verify, failures enter the standard menu

4  PAYLOADS   a robot-resident binary that is neither dimos nor helm
              go2web today; any vendor bridge tomorrow
              payload.deliver: fetch for the robot's arch, install, register a
              service, verify it is PUBLISHING — not merely that a file exists

5  CONFIG     what the robot should RUN once it is set up
              blueprint, transport, env; written into dimos config so that
              `dimos run` works with no arguments afterwards

Pure manifest becomes a Turing tarpit. Pure scripts are unreviewable, with no dry-run or resume. Compiled-in Rust traits force a third party to fork the tool, which kills sharing outright. First-party apps use the same external format, so the format is dogfooded from day one.

Steps carry a phase, and the code forces it. The Unitree Python bindings depend on the venv helm creates, so they cannot run before it. An app is not "set up, then install" — it is pre-helm steps, then helm, then post-helm steps. Any simpler model cannot express the G1. 
bringup → match → confirm → params → pre-helm → HELM → post-helm → verify

Entitlements — an app declares what it will touch

Taken from WendyOS, where an app is scaffolded with --entitlement gpu,usb,persist and the runtime knows what it asked for. An infect app does the same: it declares, in data, everything it intends to touch on your machine and on the robot.

[entitlements]
laptop = ["sudo", "net.configure"]      # will create an nmcli profile, needs root once
robot  = ["ssh", "sudo", "systemd"]     # will log in, run sudo, register a service
network = { subnets = ["192.168.123.0/24"], ports = [22, 9991] }
writes  = ["~/dimos", "~/cyclonedds", "/etc/systemd/system"]

Two things this buys, and the second is the one that matters.

  • The operator sees it before trusting it. Installing a third-party app shows the declaration: this app wants root on your laptop, ssh to the robot, and writes to three paths. That is a decision a person can actually make, unlike "run this script".
  • The core can enforce it. A step whose verb needs an entitlement the app never declared is refused before it runs — so the manifest is not documentation that drifts, it is the permission set. An app that quietly grows a new capability fails rather than succeeding silently.
Does helm have anything like this today? No. Grepping for entitlements, capabilities or declared permissions turns up nothing — the only hits are a systemd availability message and file-mode constants. Helm asks for sudo at the moment it needs it and that is the whole model. Which is correct for helm: it is one program with a fixed job, and there is no third party to constrain. Entitlements exist because apps are the thing strangers write.

The real output is a configured robot

An install that finishes and leaves you working out which blueprint to run, with which transport, against which IP, has not finished. So the last thing an app does is write the robot's dimos configuration — and the measure of success is that dimos run then works with no arguments.

# G1 — the robot runs its own stack
[config]
blueprint = "unitree-g1"
transport = "lcm"

# Go2, webrtc lane — the laptop drives, and needs to know where the robot is
[lane.webrtc.config]
blueprint = "unitree-go2"
env       = { ROBOT_IP = "{robot_ip}" }

# Go2, zenoh lane — no address at all; zenoh discovers the bridge
[lane.zenoh.config]
blueprint = "go2-zenoh-nav"
transport = "zenoh"

Those three blocks are the difference between the lanes, stated once. The WebRTC lane needs a robot IP because it dials a specific machine; the zenoh lane needs none because go2web announces itself and the laptop finds it. An operator does not have to know that — they pick a lane, and the app knows what configuration that lane implies.

This is also what makes infect the way you set up any robot rather than a bring-up script that happens to run an installer. Setting up a robot means: reach it, identify it, give it what it needs, and leave it configured to run. The install is one step of four.

The G1 app

apps/g1/app.toml

infect_api = 1

[app]
name="unitree-g1"  extends="unitree"  target="robot"      # shape 1: helm on the Jetson

[params]
wifi_ssid     = { prompt="Office wifi name",     type="string" }
wifi_password = { prompt="Office wifi password", type="secret" }

[match]
threshold = 60
[[match.probe]] kind="ping"        addr="192.168.123.164" transport="wired"  weight=50
[[match.probe]] kind="remote-glob" glob="~/*_unitree_install" capture="model" weight=40
[[match.probe]] kind="remote-file" path="~/unitree_sdk2-main/example/humanoid" weight=30
[[match.probe]] kind="ping"        addr="192.168.123.120"                    weight=10

[network]
wired = { laptop_addr="192.168.123.100/24", robot_addr="192.168.123.164" }
hint_on_no_reply = "the G1 has two ethernet jacks, try the other one"

[ssh]
user="unitree"  password="123"  install_key=true

[[step]] id="wifi" phase="pre-helm" on="robot" verb="wifi.join"
args   = { iface="wlan0", ssid="{wifi_ssid}", psk="{wifi_password}", key_mgmt="wpa-psk" }
verify = { verb="net.has-inet" }

[[step]] id="jetson-perf" phase="pre-helm" on="robot" verb="jetson.max-perf"
verify = { shell="nvpmodel -q | grep -q 'NV Power Mode: MAXN'" }

[[step]] id="cyclonedds" phase="pre-helm" on="robot"
script="unitree:steps/cyclonedds_build.sh"  timeout_s=1800
verify = { shell="test -d ~/cyclonedds/install" }

[helm]
mode="dev"  extras=["unitree"]  smoke_blueprint="unitree-g1"

[[step]] id="unitree-python" phase="post-helm" on="robot"
script="unitree:steps/unitree_python.sh"
verify = { shell="…/.venv/bin/python3 -c 'import unitree_sdk2py'", fresh_shell=true }

Read top to bottom, this is Krishna's bring-up guide as data. The probes are how infect recognises a G1 — pinging the Jetson is worth 50, the vendor install directory another 40, and 60 clears the bar. Each step carries a machine-checkable proof rather than a claim. His WPA3 workaround stops being a paragraph someone must remember and becomes key_mgmt = "wpa-psk", where the verb consuming it makes the failure impossible rather than documented. The fresh_shell on the last verify encodes the guide's known ordering trap: the installer exports CYCLONEDDS_HOME after its own check, so the import only succeeds in a shell started afterwards.

The Go2 app, both lanes

One app, two lanes, because it is one robot the operator has to choose a stack for. The lane decides where helm runs and whether a payload is delivered.

infect_api = 1

[app]
name="unitree-go2"  extends="unitree"

[match]
threshold = 50
[[match.probe]] kind="port-sweep" subnet="{subnet}" port=9991 capture="robot_ip"
                for_match=true  weight=50                # WebRTC control port
[[match.probe]] kind="remote-glob" glob="~/*_unitree_install" capture="model" weight=30

[lane.webrtc]                                            # shape 2 — the default
target = "laptop"                                        # robot never receives code
description = "laptop runs everything; robot is a peripheral"
[lane.webrtc.helm]
mode="dev"  extras=["unitree"]  smoke_blueprint="unitree-go2"
[[lane.webrtc.step]] id="robot-ip" phase="post-helm" on="laptop" verb="env.set"
args = { key="ROBOT_IP", value="{robot_ip}" }

[lane.zenoh]                                             # shape 3 — go2web
target = "laptop"
description = "go2web bridge onboard: PointLio + H.264 on the robot, dimos plans on the laptop"
[[lane.zenoh.step]] id="bridge" phase="pre-helm" on="robot" verb="payload.deliver"
args = { payload="go2web", arch="aarch64", service=true }
verify = { verb="zenoh.has-topic", args={ key="dimos/odom/*" } }
[lane.zenoh.helm]
mode="dev"  extras=["unitree"]  smoke_blueprint="go2-zenoh-basic"

The zenoh lane is where the third shape earns its keep. payload.deliver is a core verb that puts a native binary on the robot and registers it as a service — the same machinery for go2web, for a future bridge on another vendor's robot, or for anything too latency-sensitive to run off-board. The verify is not "did the file copy" but "is the bridge publishing" — zenoh.has-topic against dimos/odom/*, which is the wire contract the dimos module already declares.

What the zenoh lane confirms about the design. go2web is a Rust binary on the Go2's own computer that runs Point-LIO and encodes H.264 onboard, then publishes over zenoh. leshy's PR calls it the "dimos-helper" and notes it replaces WebRTC, the Jetson and Unitree's own services — so the robot needs no add-on compute at all. Zenoh auto-discovers, so this lane needs no networking step and no robot IP: dimos --transport=zenoh --dtop run go2-zenoh-nav. Source lives at github.com/dimensionalOS/go2web, tracked as DIM-1406; how a payload is built and fetched is the one part of shape 3 still open.
Unverified. Which extras the WebRTC lane needs. The compat engine excludes the driver on old aarch64, and what the Mac that drove greenwald actually had installed is recorded nowhere.

Match engine

infect/src/identify.rs

#[serde(tag = "kind")]
pub enum Probe {                        // closed set — read-only by construction
    Ping       { addr: String, transport: Transport, weight: u32 },
    TcpPort    { addr: String, port: u16, weight: u32 },
    PortSweep  { subnet: String, port: u16, capture: Option<String>, weight: u32 },
    RemoteFile { path: String, weight: u32 },
    RemoteGlob { glob: String, capture: Option<String>, weight: u32 },
    SshBanner  { addr: String, contains: String, weight: u32 },
}

pub fn identify(apps: &[AppManifest], facts: &Facts) -> Identified {
    let mut out = Vec::new();
    for app in apps {
        let mut c = Candidate::new(&app.app.name);
        for probe in app.matcher.ordered_probes(facts) {
            if let Some(hit) = probe.run_readonly(facts) {
                c.score += hit.weight;
                c.evidence.push(hit.describe());   // "ping 192.168.123.164: 1.2ms"
                c.captures.extend(hit.captures);   // model = "g1plus_pc4"
            }
        }
        if c.score > 0 { out.push(c); }
    }
    out.sort_by_key(|c| Reverse(c.score));
    match out.first() {
        Some(best) if best.score >= threshold_of(apps, best) && unambiguous(&out)
            => Identified::Proposed(best.clone()),  // still confirm before acting
        _   => Identified::NeedsPicker(out),
    }
}

Every app scores itself against the machine in front of you; the highest wins if it clears its own threshold and nothing else is close. Two properties matter. The probe list is a closed set of read-only operations, so no app author can smuggle a state change into identification. And every probe that fires records its evidence in words, so the operator sees why infect thinks this is a G1 instead of being asked to trust it.

Every step ends in something a machine checked — carrier up, ping answered, unit active, helm exit 0 — never in a claim. A journal per robot means a re-run resumes rather than restarting.

When a step fails

  ✗ [3/8] wifi failed: nmcli: Secrets were required (7)
    1) retry   2) fix manually (shell)   3) get help   4) let the agent try

The first three are helm's existing recovery menu, which drops you into a shell and resumes afterwards. The fourth is new, and it obeys one rule: the manifest's verify is ground truth, never the agent's claim. The agent proposes into the same machinery the operator uses and gets no private path.

  • Ambiguous match — it receives the fact table and every app's probes and notes, may compose more probes only from the read-only vocabulary, and proposes a candidate with evidence for the operator to confirm.
  • Step failure — it receives the step, the transcript, and the app's [notes], which is the guide's troubleshooting table as structured data. Destructive commands are shown before running. Success means the step's own verify passes on re-run.
  • No app exists — infect app new --assist drafts a manifest from a live session against an unknown robot.

With no model configured the menu loses item four and everything else works unchanged. That is the test of whether the agentic part is real or decorative.

Adding a robot

$ infect app new my-robot          scaffolds app.toml + steps/ + README
$ infect app test my-robot         probes against a live device, no state change
$ infect app run my-robot --dry-run
$ infect app publish               opens a PR to the apps repo

Apps live in a git repository, not a registry — lightest thing that supports sharing and review. infect app add <git-url> installs a third-party app with a trust prompt, because an app runs shell on your robot as a sudo-capable user. That is the honest scope of the sandbox: a bad app cannot corrupt infect's core or another app, but it can certainly damage the robot it was pointed at.

How we test it

  1. Contract tests, no hardware. Assert dim doctor --json and dim plan --json shapes, and that a forced stage failure exits 1. Seconds to run, and it is the test that catches the exit-code bug.
  2. Manifest and match tests, no hardware. Probe scoring against recorded fact tables is a pure function — the same trick that got plan.rs thirteen tests covering hardware nobody owns. Assert that G1 facts pick the G1 app, that Go2 facts never do, that ambiguity reaches the picker, and that no probe variant can mutate.
  3. The fake robot. Helm already ships a Dockerfile impersonating a Jetson — fake nvidia-smi, fake /etc/nv_tegra_release, fake nvpmodel. Add the vendor directories and the whole pre-helm and post-helm sequence runs against a target that cannot be damaged. Highest-value thing to build.
  4. The real G1, in order. First settle whether the ros:foxy(1) noetic(2) login selector is interactivity-guarded — if it is not, every non-interactive ssh step hangs and the verb layer is invalid. Then dry-run end to end. Then run to the helm hand-off and stop. Then let helm run, and measure it, because a 3.7 GB venv over office wifi is unmeasured and a timeout mid-uv sync is the one failure a journal cannot resume. Then re-run on an already-infected robot: every step must skip.
  5. The Go2, which tests the architecture rather than the code. It inverts every G1 assumption — wifi instead of ethernet, helm on the laptop, no CycloneDDS, and in the zenoh lane a resident payload instead of an install. If both robots work without helm learning anything about either, the boundary is right.

Build order

  1. Helm exit-code accumulator. Hours. Everything is built on it.
  2. doctor --json and plan --json. The contract. Days.
  3. Helm universality — os-release parsing, musl, the package-manager layer, preflight wired up. This is what earns the word.
  4. Infect skeleton — manifest, probes, match, journal. No hardware needed.
  5. The verb layer, ported from the code being deleted: net.wired-profile, wifi.join, ssh.install-key, jetson.max-perf, helm.deliver, payload.deliver.
  6. The G1 app — fake robot first, then the real one.
  7. The Go2 app, both lanes. The boundary test.
  8. Delete from helm. Last, and only once infect demonstrably replaces each piece.
Nothing is deleted until it is replaced. At every point in this sequence, a robot can still be brought up with the tool that exists today. The deletion is the reward for infect working, not a step on the way there.

Open questions

  • How a payload is built and fetched. go2web's source is located — github.com/dimensionalOS/go2web, with a README documenting deployment — but it is private and unread from here. payload.deliver needs its build, version and fetch story. Tracked as DIM-1406.
  • Contract drift is the top long-term risk. Two repos shipping separately, with no contract test in infect's CI against a pinned helm, and the JSON shapes rot exactly as the exit code already has.
  • Which extras each Go2 lane needs. Currently a guess.
  • Large asset delivery. The Go2 replay smoke wants a multi-GB recording that exists only on your machines.
  • How extends merges — whether base probes add to both children's scores, and how steps and blueprint maps compose.
