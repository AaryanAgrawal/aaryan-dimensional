DIOS Package Dependency Architecture

DIOS Package Dependency Architecture

Private technical proposal for team review

Product requirements: DIOS PRD

This document follows the shape of the Dimos Web proposal in issue #2710: establish the base flow, compare the meaningful alternatives, recommend one, and provide a code skeleton that makes the boundaries concrete.

Base flow

Every runnable DimOS module is a directory containing module.py and info.yaml. The YAML file is general module metadata, beginning with dependency information but able to grow as new metadata is needed. Existing package files remain the version authorities: pyproject.toml and uv.lock for Python, Cargo files for Rust, CMake files for C++, and Nix flakes for Nix.

blueprint
   │ resolves to runnable modules
   ▼
adjacent module.py + info.yaml pairs
   │ merge and deduplicate
   ▼
DIOS plan ── review ── install ── verify
   │
   └── local JSON receipt

DIOS Doctor ── diagnose release requirements ── ready, or recommended next action

The metadata supplies the information the existing language build files cannot: which operating system packages provide native libraries and which external runtime capabilities must be ready. It never contains arbitrary shell commands.

schema: 1

package_managers:
  apt:
    - libeigen3-dev
  brew:
    - eigen
  nix:
    - eigen

custom_dependencies:
  lcm_network:
    receive_buffer_bytes: 67108864
    loopback_multicast: true
  rust:
    installer: rustup
    version: 1.93.1
    components: [rustfmt, clippy]

schema: 1 is the only field required in every info.yaml. Readers reject unsupported schema versions; all other fields may evolve compatibly within the schema through optional additions and validation. Module identity comes from the directory path beneath the DimOS module root and is not repeated inside the file. CI rejects module.py without adjacent info.yaml, and info.yaml without adjacent module.py. Use a strict, portable YAML subset: mappings, lists, strings, numbers, booleans, and comments only. Do not allow anchors, aliases, custom tags, merge keys, or executable extensions. Validate every file against the schema in CI before it ships.

DimOS has one root pyproject.toml, not one per module. Its broad optional-dependency groups, such as sim, mapping, and unitree, remain owned by pyproject.toml and uv.lock. info.yaml does not repeat or infer Python packages, versions, or extras.

Each custom_dependencies entry is a dictionary of declarative data. Its shape belongs to a named, trusted DIOS handler. The LCM handler understands network buffer and multicast fields; the Rust handler understands rustup, toolchain version, and components. Metadata may never contain shell commands, scripts, or install/check commands. DIOS handlers own privileged operations, version checks, validation, and recommendations.

If multiple selected modules declare the same custom dependency, their dictionaries must be identical in schema 1. A mismatch is a resolution conflict shown before setup or update changes the machine.

Architecture alternatives

1. Who owns the dependency inventory?

A. Central DIOS catalog

DIOS owns a catalog that maps logical package names to apt, Brew, and Nix packages.

Advantages: one controlled list; aliases can hide platform naming differences.

Disadvantages: creates a new package database, duplicates module knowledge, and requires DIOS changes whenever a DimOS module adds a dependency.

B. Module-owned metadata — recommended

Each runnable module owns its operating-system packages and named runtime requirements.

Advantages: dependency changes travel with code; CI can review both in the same PR; no separate registry drifts from DimOS.

Disadvantages: provider names repeat when multiple modules use the same native library.

C. Infer everything from imports and build files

DIOS scans Python imports, CMake, Cargo, and Nix automatically.

Advantages: little authoring work.

Disadvantages: an import does not identify its apt or Brew provider; optional and runtime-only dependencies are ambiguous; inference cannot be a reliable installation contract.

2. How are missing dependencies diagnosed?

A. Automatically install missing packages

Convenient, but startup unexpectedly mutates a workstation or a physical target and may require privilege, network access, or a restart.

B. DIOS Doctor — recommended for the MVP

DIOS Doctor resolves the selected DimOS release’s module set, checks its requirements, diagnoses what is missing or incompatible, and recommends the next action. It remains read-only.

This replaces today’s incomplete behavior, where dimos run catches a short hard-coded list of missing Python imports and installs the corresponding extra.

C. Do nothing at runtime

Setup stays simple, but dependency failures remain late import, linker, daemon, or hardware errors.

Execution modes

Every mutating DIOS flow—local setup, robot preparation, and update—uses the same execution contract. DIOS Doctor uses the same reporting contract but is always read-only.

Mode Contract
Default interactive Explain the plan, request required values, ask for approval before mutation, and show proofs as steps finish.
Verbose Include every resolved action, provider decision, target, proof, and observed version without exposing secrets.
Dry run Resolve and display the complete plan and diagnostics without changing files, packages, services, local state, or the target.
Non-interactive Never prompt; use explicit inputs and documented defaults, and fail when a required human decision is missing.
Agent Non-interactive plus stable machine-readable results containing the failed step, reason, and required human decision.

These modes compose: verbose can be used with interactive, dry-run, non-interactive, or agent runs. Dry-run and Doctor produce zero mutations. Secrets never appear in output, logs, process arguments, receipts, or machine-readable errors.

3. Where does state live?

A. Local JSON only — recommended for the MVP

Module metadata ships with DimOS. DIOS writes installation receipts under its local data directory. Setup and DIOS Doctor work offline.

B. Cloud-authoritative dependency service

A service owns manifests, policy, resolution, and receipts.

This provides centralized policy and fleet visibility, but makes installation depend on identity, availability, synchronization, and an API before the local contract is proven.

C. Local authority with an optional cloud control plane — future recommendation

The local engine remains authoritative. A cloud service may distribute signed policy/catalog snapshots and accept receipts. Losing the network never prevents a known local setup or diagnosis.

               future, optional
┌───────────────────────────────────────┐
│ API + signed catalog + receipt ingest │
│ object storage + relational metadata  │
└──────────────────┬────────────────────┘
                   │ sync
                   ▼
┌───────────────────────────────────────┐
│ DIOS local engine                     │
│ info files → plan → providers → receipt│
└───────────────────────────────────────┘

The cloud API should exchange versioned catalogs and receipts, not remote shell commands. A simple future stack could use a stateless HTTP API, object storage for signed catalog artifacts, and a relational database for catalog metadata and receipt indexing. This is deliberately outside the MVP.

Proposed future cloud skeleton:

cloud/dependencies/
├── api/                 stateless authenticated HTTP service
├── catalog/             signing and compatibility validation
├── migrations/          catalog metadata and receipt index
└── openapi.yaml         versioned API contract

GET  /v1/catalogs/{dimos_release}      → signed catalog artifact
POST /v1/receipts                      → accept an installation receipt
GET  /v1/targets/{target_id}/receipts  → installation history

The local ReceiptStore trait in the skeleton is the seam for an optional cloud receipt sink. A cloud implementation queues locally first and uploads later; it never replaces the local receipt. Catalog downloads are immutable, signed inputs cached on disk. They may add organization policy, but cannot add executable commands to module metadata.

Recommended MVP

  1. Put one module.py and one info.yaml together in every runnable module directory, beginning each metadata file with schema: 1.
  2. Add a DimOS CI validator and Greptile review rule that reject missing pairs, unsupported YAML, executable fields, unknown custom handlers, and conflicting selected requirements.
  3. Package the metadata files with DimOS releases.
  4. Add DIOS metadata parsing, merge, provider planning, diagnosis, and a local JSON receipt.
  5. Extend DIOS Doctor to diagnose the selected release’s complete dependency set and recommend the next action.
  6. Keep Python packages and extras in the root pyproject.toml and uv.lock; do not duplicate or infer them from module metadata.
  7. Add no cloud dependency, account system, or remote state to setup.

Ownership and versioning

Item Owner Version source
Python package or extra DimOS repository Root pyproject.toml and uv.lock
Rust crate Native module Cargo.toml and Cargo.lock
C++ build relationship Native module CMakeLists.txt
Nix closure DimOS release flake.nix and flake.lock
apt/Brew package name Module info.yaml Native repository resolves; receipt records observed version
LCM network config, Rust/rustup, ROS, CUDA, Docker, JetPack, Deno Named DIOS handler Declarative metadata plus observed machine capability

DIOS package providers own generic commands for install, query, and verification. Modules cannot provide commands. Manufacturer SDK, firmware, and robot service requirements live in the separate manufacturer repository and use the same contract.

Code boundary

The skeleton under src/pkg/dependencies/ defines four separable parts:

  • info: the parser for the checked-in info.yaml module contract;
  • plan: deterministic merge and deduplication;
  • provider: trusted apt/Brew/Nix adapters and named custom-dependency handlers;
  • receipt: local, replaceable persistence.

The engine depends on provider and receipt traits. A future signed catalog or cloud receipt sink can implement an additional boundary without changing module metadata or the local setup flow.

Decisions requested from the team

Accepted

  1. Each runnable module is a directory containing adjacent module.py and info.yaml files.
  2. The file uses a strict YAML 1.2 subset.
  3. schema: 1 is the only universally required field.
  4. Operating-system package lists live under package_managers.
  5. Dependencies that package managers cannot fully represent live under custom_dependencies. Each entry is an open dictionary interpreted by its trusted DIOS handler.
  6. LCM system configuration and Rust installed through rustup are custom dependencies.
  7. Module identity comes from the directory path and is not repeated in the YAML.
  8. Module metadata is declarative and cannot contain executable commands at any nesting level.
  9. Conflicting definitions of the same custom dependency block planning before mutation.

Still to approve

  1. Approve direct apt/Brew/Nix names in the MVP instead of a central alias catalog.
  2. Approve DIOS Doctor as the single read-only diagnostic and recommendation experience.
  3. Approve local JSON as authoritative state, with cloud synchronization deferred and optional.
