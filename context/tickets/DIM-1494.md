## Hardware

**FSM never leaves `ZERO_TORQUE`.** Nothing calls `G1HighLevelDdsSdk.stand_up()`
(ZERO_TORQUE → DAMP → AI_MODE → SQUAT_STANDUP_TOGGLE). `start()` only calls
`_select_motion_mode()`, which sets motion mode "ai", not the FSM state. Nav plans; the robot
physically cannot move. Measured live: `get_state()` → `ZERO_TORQUE`.

**open3d dies on static TLS.** Every `PointCloud2` decode throws
`libgomp.so.1: cannot allocate memory in static TLS block` — 11,452x in one run while `[err]`
stayed 0, so no costmap and the stack looks healthy. Root cause: `LCMEncoderMixin` overrides
`subscribe()` and warms the decoder there (`encoders.py:107-116` → `PointCloud2.lcm_warmup`), but
never overrides `subscribe_all()`; `lcmpubsub.subscribe_all` (`:94`) routes to the raw pattern
subscribe, so subscribe-all consumers (rerun bridge, spy) decode with open3d never warmed. The
import then runs late inside `lcm_decode`, after the TLS budget is spent by the ONNX runtime
sharing that process. Proof it is the un-warmed path and not luck: a warmed subscribe caches
open3d in `sys.modules`, so `lcm_decode` could not fail — we saw 11,452 successful subscribes then
11,452 failed decodes. `--n-workers 12` does not fix it (538 in 150 s).
`LD_PRELOAD=/lib/aarch64-linux-gnu/libgomp.so.1` does (→ 0, costmap builds, dropped clouds 266 → 1).
glibc 2.31 predates the `glibc.rtld.optional_static_tls` tunable.
Jeff hit the same class of failure in `2ffbc74d7` (2026-05-04) and worked around it with a lazy
import — see the comment at `cmu_nav/main.py:175`.

**`unitree-g1-groot-wbc` cannot start on hardware.** `groot_wbc.py:342` builds
`PointLio.blueprint()` with no IPs while `onboard.py:26` passes `G1.lidar_host_ip` / `G1.lidar_ip`.
Exits with `PointLio: lidar_ip not set`. Workaround `DIMOS_POINTLIO_LIDAR_IP=192.168.123.120`.

**`g1.urdf` regression — fixed by Jeff in `a7327998b`.** Branch deleted the file while the blueprint
still pointed `_G1_URDF_PATH` at it, raising on every `/odometry` message. Reproduced on the robot,
verified fixed there: `pelvis->mid360 = [-0.00368, 3e-05, 0.46018]`. CI missed it because the G1
blueprint test skips on missing `unitree_sdk2py`.

## Ticket items 3 and 4 — diagnosed, not fixed

**CMU nav needs TF for no `mount`.** The only tf publisher is PointLio, emitting
frame_id → sensor_frame_id. Nothing publishes sensor → body, so terrain heights reference the lidar
~1.26 m up instead of the base. Go2 has `Go2Mid360StaticTf`; G1 has no equivalent. Cross-check:
`G1.internal_odom_offsets["mid360_link"].z` = 1.2 m, URDF puts mid360 0.46018 m above pelvis
(0.74 + 0.46 = 1.20). Likely moot: cmu_nav was deleted from main on 2026-08-20 (`9a12e1ff6`,
#3576) but still exists on `jeff/clean/g1` — a merge conflict waiting to happen.

**Groot sees its own hands.** Hardware only: in sim robot geoms are groups 0/1 and the raycast
casts only against 2/3. No self filter in PointLio → RayTracingVoxelMap → CostMapper; the only
guard is `PointLioConfig.blind = 0.5 m`. On the real URDF at GR00T default arm pose (14 zeros),
6 of 30 arm links sit outside the blind radius — index/middle finger links at 0.522-0.560 m.
