Reviewing a Large Change for Release

Five people reviewed 213 commits of a robot installer before tagging it. This is what they ran, what they found, and — more usefully — which of their findings did not survive being argued with.

The product is dim: a single binary that provisions robots, installed by a public one-line curl. It runs unattended on machines nobody is watching. That last fact decides almost every severity call below.

01Establish the shape first

You cannot read 213 commits. You can read the shape of them in about ten minutes, and the shape tells you where to spend the rest of the day. Do this before you form any opinion about quality, because your first opinion will otherwise be about whichever file you happened to open.

Start with volume, dates, and how much of the log is real work:

the ten-minute orientation
BASE=c26f534; HEAD=origin/main

# how many commits, over what period
git log --oneline $BASE..$HEAD | wc -l
git log --format='%ad' --date=short $BASE..$HEAD | sort | sed -n '1p;$p'

# how many are bare version bumps with no code
git log --oneline $BASE..$HEAD | grep -icE ' (release|bump) '

# net change: what actually landed
git diff --numstat $BASE..$HEAD |
  awk '{a+=$1; d+=$2} END {print a" added, "d" deleted, "a-d" net"}'

# gross change: what was written along the way
git log --numstat --format= $BASE..$HEAD |
  awk '{a+=$1} END {print a" lines written across all commits"}'

Those last two commands are the ones people skip, and they were the most informative in this review. Commits wrote 40,748 lines to land 14,216. Roughly 65% of everything written in the range was also deleted inside the range. A number like that is not a code-quality signal, it is a history signal: something was built and rebuilt.

Why churn matters Net diff tells you what you are shipping. Gross churn tells you how confidently it was arrived at. A 65% churn ratio means most of the diff you are about to read is archaeology.

Next, find out which parts of the system moved, and what is new:

where the change actually landed
# group the diff by top-level area
git diff --numstat $BASE..$HEAD |
  awk '{split($3,p,"/"); k=p[1]"/"p[2]; a[k]+=$1; d[k]+=$2}
       END {for (x in a) printf "%-30s +%-7d -%d\n", x, a[x], d[x]}' |
  sort -k2 -r | head -20

# biggest files that did not exist at BASE
git diff --numstat --diff-filter=A $BASE..$HEAD | sort -rn | head -15

# files added inside the range that are already gone again
git log --diff-filter=A --name-only --format= $BASE..$HEAD | sort -u |
  while read -r f; do
    git cat-file -e "$HEAD:$f" 2>/dev/null || echo "added then deleted: $f"
  done

That last loop is the churn detector in concrete form. It listed a desktop application that had been built in the repository three separate times — dashboard/, then src/dashboard/, then src/desktop/ — before being extracted to a different repository entirely. Everything left behind from those three attempts was, by definition, dead.

Two findings came directly out of that one observation, before anyone had read a line of the language: about 700 lines of code that no longer compiles but had still been receiving maintenance commits, and a 145 KB minified JavaScript bundle committed to git for a template nothing references.

The same pass named the two biggest new files — one at 1,998 lines, one at 899 — which is where you read carefully. Two of the four findings that survived to the end of the review live in those two files. And it identified the one area genuinely reworked rather than accreted (the installer core, +2,692/−1,277), which is the part a release actually turns on.

The shape is not a preamble to the review. It is the reason you look where you look.

02The passes that find shipping-grade problems

These run in seconds and each covers a category of thing that is expensive to ship. Point them at the lines the range added, not the whole tree — you are reviewing a change, not auditing a codebase, and the difference is usually a factor of ten in noise.

Secrets and personal paths

git diff $BASE..$HEAD | grep '^+' | grep -inE \
  'AKIA[0-9A-Z]{16}|BEGIN [A-Z ]*PRIVATE KEY|xox[baprs]-|ghp_[A-Za-z0-9]{36}|(api[_-]?key|secret|passwd|password|token)[[:space:]]*[:=]'

git diff $BASE..$HEAD | grep '^+' | grep -nE '/home/[a-z]+/|/Users/[a-z]+/'

The second one catches a real and common embarrassment: a hard-coded path to somebody's laptop that works on exactly one machine. Both returned nothing here, which is worth reporting — a review that only lists defects tells the reader nothing about what was checked and cleared.

Debug leftovers

git diff $BASE..$HEAD -- '*.rs' | grep '^+' |
  grep -nE 'dbg!|TODO|FIXME|XXX|HACK|eprintln!\("DEBUG'

# code that was commented out rather than deleted
grep -rn '^[[:space:]]*//[[:space:]]*println!' src/

# and just look at the repository root
git ls-tree $HEAD --name-only

All three found something. Exactly one TODO in the added code: // TODO: check me for escaping issues, sitting above a line that interpolates environment values into a systemd unit — inside a commit whose message was “fix all shell escaping holes.” The commented-out println! pass found fourteen lines in verify.rs: the block that used to tell the user, at the end of a long install, the command to actually run their robot. And plainly listing the root turned up test_sudo_env.rs and test_sudo_env.sh, two scratch probes committed months ago, which are the first thing anyone cloning the repository sees.

Cheap and high yield git ls-tree $HEAD --name-only is a one-second command that reads the repository the way a stranger does. Run it every time.

Crash surface

In Rust, .unwrap() and .expect() mean “if this fails, kill the process.” Fine in a test; bad in an installer that is halfway through modifying somebody's machine. Every language has the equivalent — an unchecked index, a bare !, a cast that throws.

git diff $BASE..$HEAD -- '*.rs' | grep '^+' |
  grep -cE '\.unwrap\(\)|\.expect\(|panic!|unreachable!|todo!'

# then check the biggest new files specifically
grep -cE '\.unwrap\(\)|\.expect\(|panic!' src/commands/desktop.rs src/commands/webserver.rs

Twenty across 14,000 added lines, and both of the largest new files contained none at all. That is a genuinely good result and it belongs in the summary next to the problems.

Privilege and destruction

grep -rn 'sudo' src/ --include=*.rs | wc -l
grep -rn 'remove_dir_all\|remove_file\|fs::write\|fs::copy' src/ --include=*.rs
grep -rn 'temp_dir()\|"/tmp' src/ --include=*.rs

The temp-directory grep is worth explaining, because it finds a specific and classic shape: download a file to a fixed, predictable path, then run it with elevated privilege. On a machine with a second user account, that user can create the file first and rewrite its contents in the window between the download and the sudo. This review found four installers and three service files staged that way.

Dry-run violations

--dry-run is a promise: print what you would do, change nothing. In most codebases it is kept by threading a boolean down through every layer, which means the failure mode is structural — a function that never receives the parameter cannot possibly honor it. So don't grep for bugs. Grep for the shape.

the tell is a literal in the flag's position
# every function that knows about dry-run
grep -rn 'fn .*dry_run' src/ --include=*.rs

# every call site that hard-codes it off
grep -rn 'spin_cmd(\|spin_cmd_with_tail(' src/ | grep 'false'

# and every unconditional write, which no dry run should reach
grep -rn 'fs::write' src/setup/

That found three separate violations, including one where --dry-run genuinely ran sudo apt-get install and another where it rewrote the user's global Nix configuration. Reading the code was enough to suspect it. Proving it took the next section.

03Build it and run it, in a sandbox

Static reading gets you suspicions. Running the thing gets you findings. Most reviewers skip this because they are afraid of wrecking their machine, and they are right to be — an installer will genuinely install things. The answer is a sandbox you can throw away, built from three pieces: an isolated $HOME, a directory of fake commands first on $PATH, and a scratch build directory.

a disposable machine, in twelve lines
SANDBOX=$(mktemp -d)
mkdir -p "$SANDBOX/home" "$SANDBOX/shim"

# fake anything that would touch the real system; log its arguments
for c in sudo apt-get systemctl launchctl brew; do
  cat > "$SANDBOX/shim/$c" <<EOF
#!/bin/sh
echo "SHIM $c \$*" >> "$SANDBOX/shim.log"
exit 0
EOF
  chmod +x "$SANDBOX/shim/$c"
done

env HOME="$SANDBOX/home" PATH="$SANDBOX/shim:$PATH" \
    ./target/debug/dim setup --dry-run --non-interactive </dev/null
echo "exit=$?"

cat "$SANDBOX/shim.log"          # what it tried to run
find "$SANDBOX/home" -type f     # what it wrote

This is the single highest-value technique in the review. Reading the source told you that install_apt_deps takes no dry-run parameter. Running it under the shim produced this, from a command the user typed --dry-run on:

SHIM sudo DEBIAN_FRONTEND=noninteractive NEEDRESTART_MODE=a apt-get update -qq
SHIM sudo apt-get install -y -qq portaudio19-dev python3-dev libgl1 libegl1

Nobody argues with a transcript. The find on the isolated home did the same job for the second violation: before the run, ~/.config/nix/ did not exist; after it, nix.conf was there with a rewritten configuration line.

Why the isolated HOME It is not only safety. It is the only way to see the complete set of files a run creates, because a real home directory is full of files you cannot attribute.

Build the ref you are shipping, not your working tree

This is easy to get wrong and one reviewer did. They ran the test suite in the checkout as handed to them and reported 40 passing tests. The checkout was ten commits ahead of origin/main on an unmerged branch. The real number for the release was 23 — a 43% overstatement, and the two best-tested new modules in that count did not exist in the release at all.

# first: is your working tree even the thing being released?
git log --oneline origin/main..HEAD
git status --short

# extract the release ref to a scratch dir and build it there
mkdir -p /tmp/rel && git archive origin/main | tar -x -C /tmp/rel
cd /tmp/rel && CARGO_TARGET_DIR=/tmp/rel-target cargo test
CARGO_TARGET_DIR=/tmp/rel-target cargo clippy --all-targets; echo "clippy=$?"

Once you have a binary, the cheapest evidence in the world is running commands. Every new subcommand's --help. Every command the README tells a user to type. The tool's own status and health checks, pointed at a fake server so you can control what they see. In this review, dim webserver status and dim desktop status both printing http://127.0.0.1:1024/ — two services claiming the same port — was found by typing both commands one after the other.

Say what your experiments did to the machine

One verifier ran cat install.sh | bash as a control experiment to check how the installer behaves with a piped standard input. That is the real installer, and it really did rewrite a systemd unit on the host. They reported exactly that, in the verdict, including what was and was not modified. A review is a document about evidence; concealing how the evidence was obtained damages all of it.

04Reachability: finding vs. noise

Here is the part that separates a review from a list of complaints. For every observation, answer one question before you write it up: what does a real user do, and what happens to them? A person, an action, an outcome. If you cannot supply all three, you have a curiosity.

The clearest example from this review looked, on paper, like one of the worst things in it.

The two reasons took four minutes to find, and they are the whole method:

trace from the code to the user, not the reverse
grep -rn 'check_extras_compat' src/ --include=*.rs
grep -rn 'PYCHECK' src/

The first grep showed that the only production caller sits after an early return that hard-codes the answer for unattended runs — so the robot path, the one the finding was built around, never arrives. The second showed three hits in the entire repository, all in the same file: the whole check is behind an environment variable that defaults to off. The commit that added the gate is titled “disable the complex pip checking system.”

So the reading was accurate and the conclusion was wrong. That happens constantly. The fix is mechanical: after you find something in a function, walk upward to its callers, and at each level look for the three things that stop execution getting there — an early return, a feature flag, and a branch on a mode the user is actually in.

A reproduction is not a reachability proof

The subtler case is worth more, because here the reviewer did run it.

The reproduction was real, and it proved the code can break. It did not prove anything reaches it — because the reviewer had written the offending line themselves, into a fake command they had put on the path. Both halves need separate evidence: this input crashes it, and something produces this input.

The cheapest counter-test When a finding names the programs that trigger it, run those programs and look at what they actually emit, and on which stream. Two minutes.

Grep for the guard before you claim its absence

One finding asserted a path-traversal risk in a hand-rolled web server, reasoning from “this file has no tests.” The router turned out to match a fixed list of exact strings, so no URL ever reaches the filesystem — and in the one place a user-supplied string did become a filename, there was a validator four lines above the call rejecting anything outside [a-z0-9-]. Absence of a test is not evidence about behavior. Before you claim a class of vulnerability, grep for its usual mitigation.

05Pre-existing is not a blocker

A release review has a range. Everything you find is either something these commits did, or something that was already true and has already shipped — here, through roughly eighty tagged releases. That distinction is not bureaucratic. It is the difference between “this change broke it” and “we have had this for a year,” and only the first is an argument for holding a tag. The second is a backlog item, and filing it as a blocker is how a review loses its authority.

Check before you write, not after:

three ways to ask “did this range touch it?”
# whole file: identical blob hashes means byte-identical
git rev-parse $BASE:.github/workflows/release.yml
git rev-parse $HEAD:.github/workflows/release.yml
git log --oneline $BASE..$HEAD -- .github/          # empty = untouched

# specific lines: -L follows a line range through history
git log -L 84,92:src/setup/mod.rs $BASE..$HEAD

# is the file new at all? non-zero exit means it did not exist
git cat-file -e $BASE:src/commands/desktop.rs; echo "existed=$?"

# read the old version of a hunk directly
git show $BASE:src/util/cmd.rs | sed -n '200,215p'

The blob-hash comparison killed a finding outright. “CI runs no tests and no lint” was filed as major by three separate reviewers — and the workflow file has the same hash at both ends of the range, last modified two days before the range began. True observation, real problem, wrong document.

git log -L is the most useful command in a release review and the least known. It takes a line range in a file and shows you only the commits that changed those lines, with their diffs. It is how you answer “who did this and when” in one command instead of a bisect.

Syntax git log -L <start>,<end>:<file> <range> — no -- before the path, and the line numbers come first.

Trap one: “pre-existing” is itself a claim

One reviewer wrote “this is pre-existing (the same loop is present at c26f534)” about a lint failure, and used it to soften their own finding. The loop was indeed present. But the linter exits 0 at the base commit and 101 at the head, because a commit inside the range changed one branch of that loop from falling through to calling exit(1) — which is exactly what made the loop vestigial and the lint fire. It was a regression, introduced here, and the reviewer had talked themselves out of it by eyeballing the code instead of running the check at both ends.

mkdir -p /tmp/base && git archive $BASE | tar -x -C /tmp/base
(cd /tmp/base && CARGO_TARGET_DIR=/tmp/t-base cargo clippy --all-targets); echo "base=$?"
(cd /tmp/rel  && CARGO_TARGET_DIR=/tmp/t-rel  cargo clippy --all-targets); echo "head=$?"

Two checkouts, one command each, and the question stops being a matter of opinion. Do this for anything mechanical: a test suite, a linter, a build for each target platform.

Trap two: pre-existing is about behavior, not lines

The strongest finding in the whole review sits on a line that is byte-identical at the base commit.

An old line plus a new condition is a new defect. The question is not “did this line change” but “what changed such that this line now fails?” Usually the answer is a new caller, a new default, or a new process that outlives the old one.

06Test coverage, honestly

Coverage invites two opposite dishonesties, and you should refuse both. The first is overclaiming — counting tests on the wrong ref, as in section 3. The second is treating “untested” as if it meant “broken.”

Get the real numbers first:

counted against the release ref
# which files have any tests at all, and how many
git ls-tree -r $HEAD --name-only | grep '\.rs$' | while read -r f; do
  n=$(git show "$HEAD:$f" | grep -c '#\[test\]')
  [ "$n" -gt 0 ] && echo "$n  $f"
done | sort -rn

# how many added lines went into files with no tests
git diff --numstat $BASE..$HEAD -- '*.rs' |
  awk '$3 !~ /compat\.rs|setup\/install\.rs/ {s+=$1} END {print s" untested added lines"}'

# how long it runs — a suspiciously fast suite is a shallow one
cd /tmp/rel && cargo test 2>&1 | tail -3

The answer here: 23 tests, 0.06 seconds, in 2 of 29 source files. 5,880 of the 7,054 added lines went into files with no tests, including both of the largest new ones. Every test exercises a pure function — building a command string, parsing a dependency expression. Nothing in the suite writes a file, starts a process, or opens a socket. And one of the 23 asserts nothing at all: it prints a table describing whatever machine it runs on, and its own comment says it is “for human inspection.” So the honest headline is 22 asserting tests, not 23.

Runtime is a coverage signal 0.06 seconds cannot include a filesystem, a subprocess, or a socket. The wall-clock time of a suite tells you what class of thing it can possibly be testing.

Then look for the structural reason, because it turns a complaint into a proposal. Here, the crate declares a binary and no library — which in Rust means integration tests cannot be written at all without restructuring first. Coverage is not shaped this way because people were lazy. It is shaped this way because the only tests that can be written are inline unit tests, which biases everything toward whatever is already a pure function.

What “no tests on the two biggest files” actually means

Precisely this: there is no automated evidence those features work, so your confidence has to come from somewhere else. It does not mean they are broken, and it is not itself a defect you can point a user at.

The review demonstrated the failure mode. One reviewer built a security case on top of the coverage gap — path traversal, malformed requests, network exposure — and three of the four claims were wrong: the traversal surface did not exist, the parser was already total, and the server binds to localhost by default. Reasoning downward from “nobody tested this” produced confident, checkable, incorrect statements. The one real bug in that file was found by reading it: an unbounded allocation sized directly from a client-supplied header.

Put the number in context, too. At the base commit the suite was 19 tests in a single file. This range added the only tests that exist outside that file. Absolute coverage went up while the ratio got much worse. Both are true, and a review that reports only the second one is arguing rather than describing.

The finding worth writing is not “coverage is 4%.” It is: the two largest new features ship with no automated evidence they work, nothing runs the suite before a release anyway, so the release's actual quality gate is a person watching a terminal — and here is the fifteen-line job that would change that.

07The public surface and its documentation

Two different questions live here, and they get conflated constantly.

Does anything that used to work stop working?

Mechanical and checkable. Diff the argument definitions and look for removals and renames:

git diff $BASE..$HEAD -- src/cli.rs |
  grep '^[+-]' | grep -E 'Subcommand|#\[arg|#\[command|long =|about ='

Five new commands, three new flags, nothing removed and nothing renamed: no existing invocation stops parsing. That is a clean result and worth stating plainly, because it is the question a release manager actually asks.

Does anything that used to work now do something different?

This is where the damage was, and no diff of the argument definitions can show it. A run with no terminal attached — a provisioning script, a CI job, a piped installer — used to install the product. It now installs the launcher, prints a success line, and exits 0. Nothing errors. Nothing in the README or a changelog mentions it; the only place it is written down is inside a help blob you have to already know to ask for.

A parse error announces itself. A silent change of meaning, with a zero exit code, is what reaches a field site.

That is the shape to hunt: behavior that changed while the interface stayed identical. Find them by diffing the entry point — the function that decides what the program does — rather than the flag definitions, and by asking what each new conditional is gating.

Read the documentation against the code

Documentation drift is not a soft finding. On the day of the tag, the README is the interface. The method has two halves and both are mechanical.

First, extract every command the docs tell a user to type, and type them.

grep -ohE '\bdim [a-z][a-z-]*([[:space:]]+--?[a-z-]+)*' README.md docs/*.md | sort -u

Then run each one in the sandbox from section 3. dim desktop --port 8088, straight out of a copy-paste block in the README, exits with error: unexpected argument '--port' found. The flag is real, but only on two subcommands the README never mentions.

Second, extract every literal the docs assert — paths, config keys, filenames — and grep the code for it. Zero hits in the code for something the documentation names is drift, every time.

grep -ohE '~/[A-Za-z0-9_./-]+' README.md AGENTS.md docs/*.md | sort -u
grep -rn 'webserver\.' src/ --include=*.rs

That pass found a support-facing log path that had moved (~/.local/share/dim/actions.log is now ~/.dimos/data/actions.log — the file you ask a field user to send you after a failed install), an install directory written without its leading dot, and four help strings documenting configuration keys that no code anywhere reads, on the same help screen as a correct list of the real ones.

The worst one was found by reading a single line. An install guide written specifically for AI agents pipes the installer to sh. The installer's first line is #!/usr/bin/env bash and its ninth is set -euo pipefail, which dash — /bin/sh on Debian and Ubuntu — rejects outright:

head -1 install.sh                       # #!/usr/bin/env bash
sh -c 'set -euo pipefail; echo ok'
sh: 1: set: Illegal option -o pipefail

Most doc bugs are minor, and the reason is instructive

It is tempting to file every one of these as major. Verification put nearly all of them at minor, on a consistent principle: they fail loudly. The --port example prints a usage error and exits non-zero before doing anything. The stale log path fails with “No such file or directory,” and four runtime surfaces print the correct path anyway. Documentation that is wrong in a way the user notices immediately is far cheaper than documentation that is wrong quietly — which is exactly why the silent zero-exit behavior change above stayed major while a dozen wrong paths did not.

08Writing it up so it gets fixed

All of the above is wasted if the write-up is not read and acted on. Four rules, each of which this review demonstrates by violating it somewhere.

Severity has to cost you something

Of the twenty-five findings filed at blocker or major, three were blockers. After a skeptical second pass: zero blockers and four majors. Everything else was minor, a nit, or wrong.

That is not a failure of the reviewers — it is what a second pass is for. But it is the number to internalize: your first instinct about severity will be too high roughly five times out of six. Definitions that hold up under argument:

  • blocker  The default path is broken. Someone following the documented instructions on a supported machine ends up worse off. Hold the tag.
  • major  A real user, on a documented path, hits this and it costs them real time or trust. Fix before tagging, or ship it written down.
  • minor  Real, but narrow, loud, or recoverable. Backlog.
  • nit  Hygiene. Free to fix, costs nothing to defer.

What separates major from minor is never how ugly the code is. It is how many users, on what path, with what recovery. The unauthenticated configuration-write endpoint stayed major because it is reachable and chains into running arbitrary code; the same server has to be turned on by hand and does not listen outside localhost by default, which is precisely why it is not a blocker. Write that reasoning into the finding. A severity is an argument, so show it.

File, line, and the command you ran

Every finding here carried a location (src/commands/webserver.rs:816) and a “how I found it.” The second is what makes a finding cheap to act on: the person fixing it re-runs your command, sees what you saw, and starts from there instead of from scratch. It is also what keeps you honest — writing down how you know forces you to notice when you don't.

State the failure, not the property

Same facts. Only the second tells anybody what to fix or how much to care. And if you cannot write the second version, treat that as a signal: you may not actually know that anyone hits it.

Check your numbers, then check them again

Every wrong number discounts every right one. Collected from this review, each inside a finding whose central point was correct:

  • “+121 lines” was +51 — the reviewer read a diffstat histogram instead of running --numstat.
  • “40 tests” was 23 — wrong ref, per section 3.
  • “5 maintenance commits” was 4, plus a repo-wide mechanical rename that touched one line.
  • “Every HTTP response with a Date header is treated as success” was really some servers, depending on header ordering — and the application's own error response was exactly 64 bytes long, so it did not trigger at all.

None of those errors changed whether the finding was real. All of them made it easier to dismiss.

Lead with a summary that is honest in both directions

The strongest summary in this review opened “Clean enough to ship, with reservations,” listed what it had looked for and not found — no secrets, no personal paths, a genuinely small crash surface, safe defaults — and then named the two things it would fix before tagging. A reviewer who reports only defects has told you nothing about the parts they checked and cleared, which is most of their work.

09When you are not sure

You will run out of time, hardware, or nerve. The correct move is to file the finding and state plainly what you did not do. “Unverified” is a first-class answer, not an admission.

The findings in this review carried an explicit flag, and the honest ones read like this: “Not exercised against a live robot.” “No Jetson available to run it on.” “Not exploited.” “Not reproduced — I did not construct a hostile PATH.” Three things that bought:

It let the second pass triage. Verified findings can be argued with; unverified ones can be reproduced or dropped. Without the distinction the two look identical and everything has to be redone.

It protected the confident findings. When every sentence in a document is hedged, the unhedged ones stop meaning anything.

It did not cost the finding its life. The strongest security result in the review — an unauthenticated endpoint that writes arbitrary configuration, which chains into running arbitrary code — was filed verified: false with the note “read the full route table; no auth check exists on any branch. Not exercised against a live robot.” Someone later ran it end to end. It held at major. Marking it unverified is what got it verified.

What “unverified” should mean is specific: I believe this from reading, here is the experiment that would confirm or kill it, and I did not run that experiment. Naming the missing experiment is the useful half. “I could not test the Intel Mac path because I do not have one” tells your reader exactly who to hand it to.

The one thing not to do is quietly promote a suspicion to a claim because it makes a better paragraph. Two of the three blockers in this review were written in the voice of certainty about consequences that had not been checked, and both ended up minor. Written as “the code is definitely wrong; I have not established that anything reaches it,” they would have cost nothing and been exactly right.

The pass, in order

  1. Shape. Commit count, date span, churn ratio, diff grouped by directory, biggest new files, added-then-deleted list. Ten minutes, before any judgment.
  2. Greps. Against added lines only: secrets, personal paths, debug leftovers, crash calls, privilege and temp-file staging, dry-run threading.
  3. Sandbox. Isolated $HOME, shimmed sudo on $PATH, the release ref extracted with git archive. Then run it.
  4. Reachability. For each observation: a person, an action, an outcome. Walk upward through callers looking for early returns and feature gates.
  5. Range. Blob hashes, git log -L, and the mechanical check run at both ends. Ask what changed such that this now fails.
  6. Evidence. Count tests on the shipping ref. Note the suite's runtime. Say what untested means and what it does not.
  7. Surface. What stops parsing, what silently changed meaning, and every command and path the docs promise, typed and grepped.
  8. Write-up. Severity you can defend, file and line, the command you ran, the failure a user hits, and an explicit unverified flag where it belongs.
