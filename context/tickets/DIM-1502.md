## The startup hazard — CONFIRMED IN CODE, and it is INVERTED (corrected 2026-08-23)

`unitree_g1_sonic_wbc.py` real-hardware branch (the `else:`, lines ~180-190):

```
_backend      = G1WholeBodyConnection.blueprint(release_sport_mode=True)
_auto_arm     = False
_auto_dry_run = True
_default_ramp_seconds = 10.0
```

`G1WholeBodyConnection.start()` calls `_release_sport_mode()`, which loops
`MotionSwitcherClient.ReleaseMode()` until MotionSwitcher reports no active controller. Unitree's
own balance controller is gone from that moment.

**The earlier note here said "nothing holds the robot up until the operator arms it". That is wrong,
and the truth is more dangerous because it is delayed.** Traced through
`g1_sonic_wbc_task.compute()` -> `tick_loop._arbitrate` -> `_write_all_hardware`:

| task state | what compute() returns | what reaches the motors |
|---|---|---|
| unarmed (the startup state) | `SERVO_POSITION` at the **current measured** angles | an active hold |
| arming (the 10 s ramp) | `SERVO_POSITION` along the ramp | actively driven |
| **armed + dry-run** | **`None`** | **nothing at all** |
| armed + live | `SERVO_POSITION` at policy targets | the policy |

`_arbitrate` does `if output is None: continue`, so an empty command dict reaches
`_write_all_hardware`, which iterates nothing. dimos stops commanding the robot entirely.

So the hazard is not at connect — at connect the task holds pose once it has seen joint state. The
hazard is **arming while still in dry-run**: the 10 s ramp drives the robot normally, and then the
instant the ramp completes the task flips to armed+dry-run and **emission stops**. A drop ~10 s
after the arm command, which reads as "it was fine, then it fell for no reason".

`auto_dry_run=True` is the shipped hardware default, so this is the default path, and "dry-run"
naming makes it sound like the safe one.

Two consequences for the first run:
- **`set_dry_run(False)` BEFORE `arm()`.** Never arm while dry-run is on.
- Gantry regardless. The window between `_release_sport_mode()` and the first tick that emits a hold
  is still unheld, and `_state_seen` gates that first emission on joint state arriving.

## What it is

NVIDIA GEAR-SONIC v1.1 as a **ControlCoordinator task** (`g1_sonic_wbc_task`), not a standalone
stack. Whole-body torque control: walking, 27 locomotion modes, mocap clip playback, upper-body
teleop. Assets pull from LFS on first run (`data/sonic`, ~950 MB).

RPCs via `task_invoke("sonic_wbc", ...)`: `set_velocity_command`, `set_locomotion_mode`,
`play_motion_clip`, `set_upper_body` (17-dof), `set_vr_3point`, `set_base_height`,
`state_snapshot`, `arm` / `disarm` / `set_dry_run`. Also speaks SONIC's native ZMQ
(SUB :5556 / PUB :5557) behind `zmq_enabled`, as an optional ingest adapter.

Upper-body targets are encoder hints, not IK: the policy follows them while keeping balance.

Files: `g1_sonic_wbc_task.py` (771), `sonic_pipeline.py` (1210), `streamed_motion.py` (260),
`zmq_wire.py` (174), the blueprint (328), plus the LFS asset and a touch to `mujoco_sim_module.py`.

## Watch for

- Whole-body torque controller, same hazard class as groot-wbc. Gantry + e-stop for the first run.
- `disarm()` is the stop, and it HOLDS current pose rather than damping — see
  [`../G1-ESTOP.md`](../G1-ESTOP.md). `arm()` is **not** safe on its own: arming while dry-run is on
  stops emission entirely 10 s later. Order is in the runbook below.
- Same environment gotchas as DIM-1494: the LCM network fixes do not survive reboot
  (`ip link set lo multicast on`, `ip route replace 224.0.0.0/4 dev lo`), and the open3d static-TLS
  failure hits any stack decoding pointclouds on the Jetson (`LD_PRELOAD=.../libgomp.so.1`).
- LFS: always `GIT_LFS_SKIP_SMUDGE=1` on checkout, then pull the sonic asset deliberately.

CHANGED — start this first, everything else is quick:

`9b0cb4cf2 feat(g1-sonic): SONIC v1.1 checkpoint` is what changed it; `sonic_pipeline.py` also moved

```bash
# 0. network fixes do not survive reboot - re-apply BOTH, every boot
sudo ip link set lo multicast on
sudo ip route replace 224.0.0.0/4 dev lo

# 1. update to the PR head (LFS off, always)
cd ~/dimos && export GIT_LFS_SKIP_SMUDGE=1
git fetch origin pim/feat/g1-sonic-wbc && git checkout -B sonic FETCH_HEAD

# 2. pull the NEW checkpoint - .lfsconfig has `fetchexclude = data/.lfs/*`,
#    so -X "" is required or the pull silently no-ops
git lfs pull -I "data/.lfs/sonic.tar.gz" -X ""

# 3. run (LD_PRELOAD or the open3d static-TLS failure kills perception silently)
LD_PRELOAD=/lib/aarch64-linux-gnu/libgomp.so.1 dimos run unitree-g1-sonic-wbc
```

Then, and only in this order:

```
robot ON THE GANTRY (or seated/damped) before launching - sport mode is released at connect
  -> wait for "Sport mode released - low-level control active"
  -> wait for the task to report started, armed=False   (it is holding pose here)
  -> task_invoke("sonic_wbc", "set_dry_run", False)      <-- BEFORE arm, never after
  -> task_invoke("sonic_wbc", "arm")                     10 s ramp to the SONIC default pose
  -> "ramp complete - policy armed" with mode=live       (mode=dry-run here means STOP, see above)
  -> task_invoke("sonic_wbc", "set_velocity_command", ...)
stop at any point: task_invoke("sonic_wbc", "disarm")    holds current pose, does NOT damp
```

`disarm()` is a hold, not a damp. The strong stop is still the physical e-stop.

### Watch the CPU

The real-hardware branch also stands up a full nav stack — `PointLio`, `RayTracingVoxelMap`,
`CostMapper`, `ReplanningAStarPlanner`, `MovementManager` — beside a 50 Hz whole-body torque policy,
at `_n_workers = 10`. During the kronknav run on 2026-08-22 `voxel_ray_tracing` alone held 177% CPU
and the Jetson sat at load 11.8 on 8 cores, which starved the raytracer's own odometry handler.
A torque controller missing ticks is a safety problem, not a lag problem. SONIC sets
`emit_every=0` / `global_emit_every=4` so it is lighter than kronknav's `emit_every=1`, but watch
`uptime` and the tick rate on the first run.
