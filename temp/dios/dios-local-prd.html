dios — Product Requirements

Status: Draft Scope: Installing DimOS on the current machine, manufacturer-owned robot wizards, and local target history Architecture: [dios-architecture.md](dios-architecture.md)

Customer message

Install DimOS here with dios setup. Prepare a robot with dios seed <manufacturer>.

dios keeps the familiar Helm setup experience for any machine. Robot-specific discovery and setup live in separate manufacturer integrations, so each manufacturer can own its complete wizard.

Problem

Installing DimOS and preparing a robot currently requires platform knowledge, setup guides, remembered addresses, and manufacturer-specific commands. A package installation can finish even when the robot cannot start a blueprint.

Robot-specific knowledge also accumulates in the core installer. This makes the generic DimOS setup flow harder to maintain and forces every manufacturer change through the same repository.

Goals

  1. Preserve and refactor the existing Helm setup experience as dios setup.
  2. Allow DimOS to be installed directly on a workstation or any other supported machine.
  3. Give every manufacturer its own repository and setup wizard.
  4. Let a manufacturer wizard reuse the same dios setup engine on a target.
  5. Prove that a seeded target can start its intended blueprint.
  6. Remember target identity and installed versions locally on the workstation.

Product shape

dios has two equally important capabilities:

Setup this machine

dios setup

Install and verify DimOS on the machine where dios is running. This is the direct successor to the existing Helm product and is a complete standalone experience. A user does not need a robot or a manufacturer integration to use it.

Seed a target

dios seed <manufacturer>

Launch a manufacturer-owned wizard that prepares a robot target. The wizard reuses dios setup on the target rather than implementing a second DimOS installer.

Neither capability is secondary: setup serves local DimOS users directly and is also the reusable installation foundation used by seed.

User experience

Install dios

bash <(curl -fsSL https://dim.bot/install.sh)

The bootstrap selects and verifies the correct dios binary, installs it, and prints the next step.

Install DimOS on this machine

dios setup

This is the current Helm setup experience, retained and cleaned up. It works on a workstation or on a target because it installs DimOS on whichever machine runs the command.

Existing choices remain:

dios setup --mode library
dios setup --mode dev

Prepare a robot

dios seed unitree

dios loads the verified Unitree integration and opens the Unitree-owned wizard. The wizard:

  1. discovers Unitree targets;
  2. identifies the model and asks the operator to choose;
  3. establishes access and performs Unitree-specific preparation;
  4. installs or transfers dios to the target;
  5. invokes the standard dios setup flow on the target;
  6. performs Unitree-specific finishing work;
  7. starts the correct headless blueprint as the final proof;
  8. records the target and versions locally on the workstation.

Other manufacturers follow the same user journey through their own integrations.

Return to a known target

dios target list
dios target show lab-g1

dios remembers target identity, previous addresses, manufacturer integration, installed versions, and the last seed result. A DHCP address change updates the known target rather than creating a new one.

User stories

Install DimOS on a workstation

As a robotics engineer, I want to run dios setup on my workstation so that I can install and use DimOS without following a manual dependency guide.

Seed a new robot

As a deployment operator, I want to launch the robot manufacturer's wizard so that I can discover, configure, and verify a target without knowing its IP address or internal setup steps.

Resume a failed setup

As an operator, I want to rerun a failed seed safely so that completed work is preserved and only unfinished or failed steps run again.

Return to a known target

As a robotics engineer, I want dios to recognize a previously seeded target after its IP address changes so that I can reconnect without scanning the network manually.

Automate routine deployment

As an automation agent, I want a non-interactive seed flow with structured failures so that I can complete routine work and clearly escalate decisions that require a person.

Build a manufacturer integration

As a manufacturer integration developer, I want to own my models, discovery logic, setup wizard, and final verification in a separate repository so that I can release changes without modifying dios core.

Diagnose a deployment

As a support engineer, I want to see which target was configured, which versions were used, which steps passed, and where a run stopped so that I can diagnose a failure without repeating the setup.

Requirements

  1. Preserve Helm behavior. dios setup retains current working setup behavior wherever it is

still correct. The work is a refactor, not a rewrite.

  1. Run anywhere supported. dios setup installs DimOS on a workstation or target using the same

core flow.

  1. Keep dios generic. dios core contains no Unitree, Go2, G1, or other manufacturer-specific

behavior.

  1. Manufacturer ownership. Each manufacturer repository owns its models, discovery, networking,

firmware rules, wizard screens, special setup, and final robot-specific proof.

  1. Verified integrations. A manufacturer integration resolves to an immutable version and

verified artifact before it runs.

  1. Review before mutation. The wizard shows the selected target, versions, and requested

permissions before making changes.

  1. Safe re-runs. Work whose proof already holds is skipped. Failed work can be retried.
  2. Real success. A robot is ready only after its intended headless blueprint runs successfully

for a bounded period.

  1. Local memory. Target identity and version information remain available with no internet.
  2. No secrets in history. Passwords and private keys never appear in local target records,

logs, or command arguments.

  1. Agent-safe behavior. Agent mode never prompts or guesses; it reports when a human decision

is required.

  1. Physical safety. No setup or version check may stop a robot already performing physical

work.

Issues

The delivery plan is the ordered issue list below. Each issue is a product milestone: it should leave the user with a complete new capability that can be demonstrated and accepted.

Issue 1 — Refactor Helm into dios setup

Preserve the existing user journey while making the setup engine cleanly reusable on both workstations and targets. This is a standalone product milestone, not merely supporting work for robot seeding.

Success criteria

  • dios setup installs DimOS on a supported workstation.
  • Library and development modes retain their current working behavior.
  • The same setup flow can run unattended on a target.
  • Existing Helm users have a documented migration path.

Issue 2 — Define the manufacturer integration contract

Specify how dios finds, verifies, launches, and receives results from a manufacturer wizard.

Success criteria

  • An integration declares its name, version, models, permissions, and wizard entry point.
  • dios verifies an integration before launching it.
  • Interactive, unattended, and agent modes have defined behavior.
  • A sample integration completes the contract without manufacturer logic in dios core.

Issue 3 — Build the Unitree wizard

Create the Unitree integration repository and move Unitree models, discovery, network preparation, setup steps, and wizard UX into it.

Success criteria

  • dios seed unitree opens the Unitree-owned wizard.
  • The wizard discovers and distinguishes supported Unitree targets.
  • It prepares a target and invokes the standard dios setup flow on it.
  • Unitree-specific code and model names no longer live in dios core.

Issue 4 — Add local target history

Support target list, target show, rename, address refresh, and installed-version display.

Success criteria

  • A seeded target appears in dios target list.
  • dios target show displays identity, addresses, integration, versions, and last outcome.
  • An address change updates the existing target instead of creating a duplicate.
  • Target history remains usable without internet access.

Issue 5 — Prove the complete journey on hardware

Install DimOS on a workstation. Then seed a clean G1, pass the headless blueprint test, repeat with no unnecessary changes, reboot, and rediscover it.

Success criteria

  • A new operator completes the documented workstation installation.
  • A clean G1 reaches a running blueprint without undocumented commands.
  • A second seed changes nothing already proven correct.
  • After reboot or DHCP change, the workstation finds the same target again.

  • A user installs and verifies DimOS on a supported workstation using only dios setup.
  • The workstation setup experience is complete without a robot or manufacturer integration.
  • A manufacturer wizard uses the same setup engine on its target.
  • A fresh G1 reaches a running blueprint without undocumented commands.
  • A second run changes nothing already proven correct.
  • The workstation recognizes the same target after its address changes.
  • Adding a manufacturer does not add manufacturer logic to dios core.

  • Remote telemetry
  • Automatic robot updates
  • Replacing a manufacturer's operating system

A1 — Key architecture decisions requiring team input

The following decisions should be reviewed with the DimOS and manufacturer-integration owners before implementation:

  1. Two equal dios capabilities. dios setup is the standalone DimOS installer for the current

machine. dios seed <manufacturer> launches a robot wizard that reuses setup on its target.

  1. One repository per manufacturer. Unitree models and the complete Unitree wizard live in a

Unitree repository. Other manufacturers follow the same pattern.

  1. Generic core. dios core contains no manufacturer models, firmware rules, discovery probes,

or wizard-specific screens.

  1. Manufacturer ownership. Each manufacturer repository owns discovery, target selection,

network bring-up, manufacturer-specific requirements, and the final robot proof.

  1. One setup engine. Manufacturer wizards prepare a target and invoke dios setup; they do not

create a second DimOS installer.

  1. Local state for this phase. Target identity, addresses, versions, and run history are stored

locally. Cloud services and licensing are outside this PRD.

  1. ROS2-style dependency declarations for every DimOS package. Each DimOS package or module

declares what it needs in a checked-in manifest, similar to ROS2's package.xml. dios aggregates these declarations for setup. This changes every package and the release process, so the team must agree on the ownership model, file format, required fields, and migration plan before the contract is fixed.

A2 — Major decision: ROS2-style package dependency manifests

Decision status: team input required. This is not only a dios implementation choice. It changes how every DimOS package declares dependencies, how a DimOS release is assembled, how manufacturer integrations request capabilities, and eventually how dimos run prepares a blueprint.

Today DimOS has no single source of truth for dependencies. Python feature sets are declared as extras in pyproject.toml, while system and native packages are maintained separately in flake.nix and installer code. These lists can drift.

The recommended model copies ROS2's separation between package declarations and rosdep mappings:

  1. Every DimOS runtime module declares logical package IDs. A blueprint can therefore list its

needs before importing or starting modules.

  1. Every logical package owns a dimos.package.toml. This is the source of truth for its direct

Python dependencies and abstract system-dependency keys. Package authors do not write install commands.

  1. One reviewed dependency catalog maps abstract keys to providers. For example,

opengl.runtime maps to apt packages on Ubuntu, formulae on macOS, and Nix attributes under a pinned Nixpkgs revision. The catalog ships with and is pinned by each DimOS release.

  1. dios contains provider adapters, not package recipes. The adapters know how to query, compare,

install, and verify uv, apt/dpkg, Homebrew, and Nix packages. No module may inject arbitrary shell commands into setup.

  1. Release tooling aggregates and locks. CI collects every package manifest, validates every

dependency key on supported platforms, generates Python extras and the release dependency catalog, locks Python with uv, and pins Nixpkgs. A release fails if the graph conflicts or a supported platform has no mapping.

  1. Profiles select packages. A release-owned standard profile is installed by default.

Optional profiles such as sim are shown during setup. Manufacturer wizards add required or recommended package IDs without copying their dependency declarations.

  1. dios records a receipt. The receipt includes the DimOS release, selected profiles, package

manifests, catalog digest, lock digests, provider used, requested constraints, and versions actually observed.

  1. dimos run performs preflight later. The blueprint registry exposes module package IDs before

importing them. dimos run asks dios to check the union. By default it prompts before installing; unattended execution fails with an exact remediation command unless installation was explicitly authorised.

Illustrative package manifest:

schema = 1
package = "dimos.simulation.mujoco"

[python]
packages = ["mujoco>=3.3.4", "playground>=0.0.5", "pygame>=2.6.1"]

system = ["opengl.runtime", "egl.runtime"]

[[platform]]
when = "linux && aarch64"
supported = false
reason = "Required simulation wheels are unavailable"

Illustrative provider catalog entry:

[dependency."opengl.runtime".apt.ubuntu."22.04"]
packages = ["libgl1"]

[dependency."opengl.runtime".brew.macos]
packages = []
provided_by_os = true

[dependency."opengl.runtime".nix]
attributes = ["libGL", "mesa"]

TOML is recommended over XML because both dios and DimOS already use TOML and it supports the required structured provider data cleanly. The architecture follows ROS2; it does not need to copy ROS2's syntax.

Version guarantees are provider-specific rather than pretending every package uses SemVer:

  • Python: PEP 508 constraints in package manifests; exact resolution from the DimOS release's

uv.lock; installation with locked uv sync and verification with package metadata plus uv pip check.

  • Nix: exact Nixpkgs and source revisions from flake.lock; verification by realised store path

and closure.

  • apt/dpkg: package constraints use Debian's native version ordering and installed versions from

dpkg. Exact reproduction additionally requires a pinned repository snapshot; without one, dios records the actual version and guarantees compatibility, not byte-for-byte identity.

  • Homebrew: Homebrew is rolling and cannot generally install arbitrary historical versions.

Normal formulae therefore provide compatibility checks and an installation receipt, not exact replay. A dependency that truly requires an exact Homebrew version must use a maintained versioned formula or a Dimensional tap.

  • Drivers, firmware, kernel modules, and vendor SDKs: these are host capabilities, not ordinary

user-space packages. They use explicit probes and manufacturer-owned rules and are never silently replaced by Nix or uv.

The standard profile, selected optional profiles, manufacturer requirements, and later blueprint requirements are merged into one plan with provenance. Conflicting constraints fail before any machine is changed.

- **Drivers, firmware, kernel modules, and vendor SDKs:** these are host capabilities, not ordinary
  user-space packages. They use explicit probes and manufacturer-owned rules and are never silently
  replaced by Nix or uv.

The standard profile, selected optional profiles, manufacturer requirements, and later blueprint
requirements are merged into one plan with provenance. Conflicting constraints fail before any
machine is changed.
